Evidence before options

Grounding Context

Codebase Context. Kinlogue 当前没有“服务端数据”；权威事实源是固定在 App Sandbox 的本机明文 Vault。完整状态不只是确认原件：library.json 与不可变对象保存成员、记录、OCR、草稿和 DICOM，lan-inbox/inbox.json 另有一套待确认手机文件状态。现有“导出原始文件 ZIP”明确排除 catalog、OCR、草稿和 inbox，不能恢复应用。

现有存储结构非常适合生成一致恢复点：不可变对象先发布、manifest 最后原子替换，VaultRevision 记录 generation、commit ID 与 catalog digest，读取和提交会完整验证对象图并失败关闭。可复用的关键先例是固定 revision 的流式原件导出；不能直接复用的是 readSnapshot，它只有 32 个对象 / 128 MiB 的上限。

iCloud 的决定性约束： Apple 当前 App Review Guideline 5.1.3(ii) 写明，健康管理类 App 不得把个人健康信息存入 iCloud。故 iCloud Drive 与 CloudKit 即使技术可行，也不应进入面向 Mac App Store 的生产路线，除非 Apple 对 Kinlogue 的具体数据流给出明确书面澄清。客户端加密不能被擅自理解为该条款的例外。

CloudKit 的私有数据库、CKSyncEngine、encrypted values 与 CKAsset 在工程上都能表达类似对象/manifest 的模型；但 Apple 也说明，用户重置 iCloud Keychain 后，加密 zone 可能永久无法解密，需要从仍存在的本地副本重建。因此它不能单独承担“Mac 与 Keychain 同时丢失”的灾难恢复承诺。

1. Provider-neutral Kinlogue Backup Format

Confidence 94%Complexity High
Description
定义独立于当前目录布局和云厂商的自描述恢复 envelope。它固定一个 Vault revision，声明备份格式、catalog/inbox schema、范围、对象清单、长度/摘要、兼容 reader 与认证信息；恢复只能先进入 staging，完成验图和版本处理后再激活。
Axis
一致快照与可恢复性
Basis
direct: docs/storage.md 证明当前 Vault 已使用不可变对象、manifest 原子提交、generation/digest 校验和非破坏性失败关闭；VaultCatalog.reachableObjectReferences 已定义 canonical 可达图。现有导出恰好因缺少恢复 manifest 而不能成为备份。
Rationale
先冻结“什么才算可恢复”，才能在不牺牲正确性的前提下比较目录、S3、R2 或未来托管服务。它还是后续版本迁移与恢复测试的长期 ABI。
Downsides
需要新的全库流式 snapshot、认证格式、容量预算、历史格式 reader/migrator 和整库激活事务；不能用短暂锁后目录复制来替代对象 pinning/lease。

2. Restore proof, not upload success

Confidence 95%Complexity Medium
Description
把“已创建”“已送达”“已验证”“已完成恢复演练”分成四个用户可见状态。只有把远端恢复点下载到隔离 staging、验证认证与对象图、执行必要迁移并以当前 App 重新打开成功，才显示最近可恢复时间点。
Axis
一致快照与可恢复性
Basis
direct: 当前导出已经在发布前复核固定 revision 和每个 entry，但文档明确它不可恢复；Vault 对缺失、损坏和不支持版本均失败关闭。reasoned: 上传成功只能证明云端收到了字节，不能证明密钥、格式和对象集合可用。
Rationale
它直接回答用户真正关心的 RPO：最近哪一个时间点被证明可以带回，而不是最近一次 HTTP 200。
Downsides
恢复演练需要额外磁盘、I/O 和后台调度；“重启打开”如何自动化必须避免让临时 Vault 污染生产身份。
3

3. 客户端认证加密 + 独立恢复秘密

Confidence 93%Complexity High
Description
每个 checkpoint 在离开 Mac 前以认证加密保护内容和敏感关系 metadata；本机 Keychain 可以保存便利解锁材料，但必须另有不依赖原 Mac、原 Keychain 或云账号的恢复秘密。首份成功备份前应完成一次重新输入或干净环境恢复验证。
Axis
隐私、加密与密钥恢复
Basis
direct: 当前 Vault 是明文，SHA-256 只检测意外损坏，不提供保密、认证或防回滚；隐私文档要求未来升级同时设计密钥生命周期、迁移、失败恢复和重启校验。external: Apple 说明 CloudKit 加密数据在 iCloud Keychain 重置后可能永久丢失。
Rationale
灾难恢复不能让“Mac 丢失”和“解密能力丢失”处于同一故障域，也不能把病历明文交给云运营者。
Downsides
恢复秘密的展示、确认、轮换、遗失与支持体验都很难；完全隐藏时间、流量和大小模式代价很高，不能宣称云端无法推断任何 metadata。

4. Two-scope recovery point

Confidence 91%Complexity Medium
Description
由一个父 descriptor 明确绑定两个可分别验证的范围：长期保留的主 Vault，以及可选或短期保留的 LAN inbox。恢复时用户可以只带回已归档资料，也可以连待确认手机文件一起恢复；进行中的 partial 和迟到任务必须有明确排除/终止语义。
Axis
备份范围与版本兼容
Basis
direct: library.json 和 lan-inbox/inbox.json 是两套独立 logical commit point；inbox 还包含 blob、derived、terminal 与 receipt。当前原件 ZIP 对这些内容全部不可达。
Rationale
“完整数据”不能是模糊承诺。把范围显式化，可避免恢复后重复投递、归档项目复活或用户以为未确认资料也受保护。
Downsides
需要定义跨两个 head 的一致 cut；inbox 的敏感性、短期价值和成本可能与主 Vault 不同，默认是否包含需要用户研究。

5. Append-only recovery ledger with retention

Confidence 90%Complexity Medium
Description
每次发布新的不可变 generation，而不是覆盖唯一的 latest.zip。保留多个已验证恢复点；“latest”只是可重建指针。S3 Object Lock、R2 Bucket Locks 等可在明确配置时增强保留，但 Kinlogue 的格式本身仍须使用不可变 key 和延迟垃圾回收。
Axis
备份范围与版本兼容
Basis
direct: 本机 Vault 已是不可变对象 + 原子 head 的结构，外部删除当前也不等于擦除历史副本。external: S3 Object Lock 依赖 Versioning 并提供 WORM 保留；R2 Bucket Locks 可阻止指定期限内删除和覆盖。
Rationale
备份不仅要抵御硬盘损坏，还要抵御误删、损坏状态同步、勒索或泄露凭据后删除所有历史。
Downsides
保留与彻底删除天然冲突；需要可解释的保留期、容量/费用预算与远端清除状态。并非所有“S3 兼容”服务都提供 versioning 或 lock。
6

6. One recovery core, three increasingly capable targets

Confidence 92%Complexity Medium → High
Description
所有目标 round-trip 同一种加密 checkpoint。第一目标是用户通过系统面板授权的非 iCloud目录（外置盘、NAS 或由其他 File Provider 同步的目录）；第二目标是客户端加密的 S3/B2/R2；只有用户量和运营能力成立后，才考虑 Kinlogue 托管服务。
Axis
云平台接入与发布门禁
Basis
direct: 当前生产已有 user-selected read/write entitlement，却没有 outbound network、iCloud 或 CloudKit entitlement，发布脚本还会拒绝额外 capability。external: security-scoped bookmarks 支持持久授权但可能 stale；Apple 当前规则阻断个人健康信息进入 iCloud。
Rationale
它先交付真实防丢失价值，同时把账号、凭据、云 SDK、数据地域和安全运营从恢复正确性中解耦。
Downsides
目录目标的外部同步状态不受 Kinlogue 控制；S3 需要 outbound entitlement、凭据或短期 token；托管服务会改变“无账号、无云服务”的产品边界并承担合规义务。
iCloud 定位：保留为政策研究项，而不是这里的一个目标。技术原型只有在 Apple 对具体用例给出可审计澄清后才有进入生产路线的意义。

7. Backup-first device continuity

Confidence 86%Complexity Medium
Description
先通过已验证恢复解决“换 Mac / 原 Mac 丢失 / 第二台 Mac 接管”：新设备恢复后显式成为唯一写入者，旧设备重新出现时不能自动覆盖远端历史。只有真实需求证明需要两台同时编辑时，才另行设计多主同步。
Axis
从单向备份演进到多设备同步的冲突与删除语义
Basis
direct: Kinlogue 当前是一台 Mac、单操作员产品；generation CAS 只解决同一 Vault root 的旧代提交冲突，不是分布式合并算法。reasoned: 换机连续性可以用完整状态接管解决，而多主同步还必须具备设备身份、因果操作、显式冲突和删除 tombstone。
Rationale
它让用户更早摆脱单机故障点，又不会把共享目录或最后写入者覆盖误称为安全同步。
Downsides
真正可靠的 writer takeover 仍需认证设备身份和远端 fencing；若用户确实长期在两台 Mac 同时编辑，它只能推迟、不能消除同步需求。

What did not survive

Rejection Summary

#IdeaReason Rejected
1短暂双 head fence 后复制短锁释放后对象仍可能被清理；必须有对象 pinning 或持有协调 lease，降为 Idea 1 的实现问题。
2历史格式恢复转换器有价值，但属于恢复协议的组件，不是独立方向。
3加密不透明布局可阻止所有推断依据被反驳：时间、大小、流量和访问模式仍会泄漏；只能作为有限 threat-model 加固。
4用户选择目录作为第一目的地保留在 Idea 6，不单独占一个方向。
5S3-compatible 目的地作为第二目的地保留在 Idea 6；“兼容 S3”本身不保证 versioning/retention。
6独立 Backup Relay隔离、认证和 entitlement 设计尚未成立，不能声称主 App 的能力边界天然不变。
7iCloud 技术分支当前是强制政策门禁，不是可推荐的生产交付方向。
8Time Machine 提示是有用基线建议，但不是 Kinlogue 可验证的恢复能力。
9只靠 writer epoch 接管没有认证设备身份和远端 fencing 就不完整；合并进 Idea 7。
10真同步 mutation ledger保存为 Idea 7 的未来触发条件；当前超出备份目标且实现负担远高于已验证价值。
11删除、保留、远端擦除三分是 Idea 4/5 必须包含的生命周期语义，不单独成为方向。
12恢复健康状态阶梯作为 Idea 2 的产品呈现方式保留。
13干净 Mac 灾难测试作为 Idea 2/3 的核心验收标准保留。
