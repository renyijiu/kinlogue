# 搜索结果呈现的规模测量与端到端核对（2026-10-14）

本页记录搜索结果卡片新增“命中表格行 / 上下文摘录”之后做的两项核对：近上限资料库上的首页计时对照，以及真实 OCR 走完导入、确认、搜索的端到端核对。功能取舍见 [`decisions.md`](decisions.md) 2026-10-14 一节，实现说明见 [`sqlite-storage.md`](sqlite-storage.md#app-查询与提交观察)。两项核对都用了临时改动，结束后已撤回，没有进入主测试清单或提交内容。

## 环境

Mac13,1 / M1 Max / 64 GB / 内置 APFS；macOS 27.0.1（26A434）、Swift 6.4。计时探针是 `-c release` 构建的 [`StorageScaleProbe`](../Sources/KinlogueStorageProcessFixture/StorageScaleProbe.swift)；端到端核对在 debug 测试进程里运行。测量期间没有运行其他构建或测试，不是冷缓存测量，也没有记录全机负载。

## 规模计时

### 方法

- 资料库：`logical-generate --reports 9990` 生成 9,791 条已确认记录和 199 份草稿，用时 362 s，数据库 504,610,816 bytes。为让新功能有东西可列，生成时临时把每份报告的检查结果换成 30 行制表符分隔的表格：每份都有一行“合成葡萄糖”，一行编号唯一的“合成指标 n”，其余 28 行“合成项目 k”；结果字段引用 30 个 OCR block。其余字段与 [2026-10-12 复测](storage-search-measurement-2026-10-12.md) 的生成方式相同。
- 查询：沿用 `logical-queries` 的六个固定词，另加两个临时词：`合成葡萄糖`（每份报告恰有一行命中）和 `合成指标4321`（只有一份报告命中）。`合成` 命中每份报告的标题，也命中结果的全部 30 行。
- 对照：同一个二进制、同一个资料库，用一个临时环境变量跳过搜索分页里的呈现步骤作为基线。每个词各采样 20 次取首页（前 100 条摘要），p50 取排序第 10 项、经验 p95 取第 19 项；“首次”是该进程里这个词第一次取首页，此前只跑过不带呈现的全量扫描。

### 结果

首页时间，单位 ms，格式为 p50 / p95（首次）。两轮结果相差不到 2 ms，表中取第一轮。

| 查询 | 命中数 | 基线 | 初版实现 | 最终实现 |
| --- | ---: | ---: | ---: | ---: |
| 无匹配 | 0 | 28.2 / 29.3（29.9） | 28.4 / 29.3 | 28.4 / 29.4（28.8） |
| 稀有词 | 1 | 29.0 / 30.0（29.2） | 28.8 / 30.4 | 28.2 / 29.2（29.2） |
| 日期 | 93 | 39.6 / 40.6（38.6） | 64.2 / 65.8 | 40.4 / 41.8（40.6） |
| 中文短词 `合成` | 9,791 | 39.5 / 40.7（39.1） | 80.5 / 82.3 | 51.5 / 52.6（61.8） |
| 成员 | 9,791 | 39.7 / 40.7（40.7） | 58.8 / 59.6 | 39.9 / 41.8（41.2） |
| `合成葡萄糖` | 9,791 | 62.3 / 63.7（61.4） | 100.2 / 102.3 | 65.3 / 67.2（64.9） |
| `合成指标4321` | 1 | 28.9 / 29.6（28.5） | 29.5 / 30.3 | 28.5 / 28.8（28.1） |

`合成葡萄糖` 的“首次”是在 `合成` 之后测的，那时前 100 份报告的结果字段位置已经记住，所以它不是这个词真正的冷启动；`合成` 的 61.8 ms 才包含 100 次详情解码。进程峰值 footprint 在 79–83 MB 之间，与基线没有可分辨的差别。

初版实现对每个列出的报告逐字段做本地化查找、整段折叠空白生成摘录，并且命中表格行时每次都完整解码详情。最终实现做了四处改动：

1. 用该行缓存里的预筛键只挑可能命中的字段，成员或日期命中时什么都不查。
2. 摘录只在命中处附近折叠空白，长字段只需一次查找。
3. 表格行按“找下一处命中、取其所在行”的方式查找，不再逐行查找；同一字段的行只算一次。
4. 结果字段在搜索字段里的位置按搜索行与详情行两个摘要记住，之后的查询不再读取详情；第一次读取时只解码结果文本，不解码来源引用。微基准里一份约 27 KiB 的详情，只解码文本约 0.08 ms，解码完整来源字段约 0.45 ms。

### 边界

- 除 `合成` 外，最终实现与基线相差不超过 3 ms。`合成` 让每份列出报告的 30 行全部命中，仍比基线多约 12 ms（首次多约 22 ms），p50 51.5 ms 略高于 50 ms 门槛；每行一次 Foundation 查找是主要开销。
- `合成葡萄糖` 的基线本身是 62 ms，已高于 50 ms 门槛：预筛键只在较长的结果字段里命中，Foundation 要在全部 9,791 行的该字段上确认，完整结果的 p50 为 50.6 ms。这与新功能无关；2026-10-12 的复测用叙述文本，没有覆盖这种数据形状。
- 只测了 macOS 27 上 Platform repository 到 DTO 的时间；安装后的 App、界面渲染、macOS 26 和 OS 冷缓存都没有测。

## 端到端核对

### 方法

临时测试用 PingFang SC 绘制 6 种合成版式，每种各生成一份带文字层的 PDF 和一张 2.5 倍分辨率的 PNG，共 12 份。版式包括：项目 / 结果 / 参考值；多一列单位；表头写成“检验项目 / 检测结果 / 单位 / 参考区间”；检验科常见的“序号 / 项目名称 / 缩写 / 结果 / 提示 / 单位 / 参考值”；两张表左右并排；超声叙述报告。每份都经过真实的 `OnDeviceTextExtractionService`、App 的导入与确认服务（按候选原样确认）和 SQLite 搜索。

### 结果

| 版式 | 图片（Vision） | PDF 文字层 |
| --- | --- | --- |
| 项目 / 结果 / 参考值 | 8 行全部抽出 | 抽不出表格 |
| 多一列单位 | 8 行，单位并入结果格 | 抽不出表格 |
| 表头别名 | 改动前抽不出；改动后 8 行 | 抽不出表格，标题误取为“检测结果 单位 参考区间” |
| 检验科常见版式 | 改动前抽不出；改动后 8 行，序号不进行内，缩写并入项目格 | 抽不出表格 |
| 两表并排 | 改动前右表并入左表的参考值格；改动后两表 8 行各自成行 | 抽不出表格 |
| 超声叙述 | 检查所见与结论正确；搜“回声”“脂肪肝”显示上下文摘录 | 同左 |

“改动”指同日的抽取规则 version 6，见 [`import-and-ocr.md`](import-and-ocr.md)。

PDF 文字层抽不出表格的原因：文字层按行生成 block，一行里的各列合成一个 block（例如“葡萄糖(GLU) 6.85 ↑ 3.89-6.11”），表头也是一个 block，表格检测找不到单独的“项目 / 结果 / 参考值”单元格。同一原因还让科室取成“内分泌科 样本：血清 采样时间：…”、报告日期候选带上“检验者”等后续文字、采样时间丢失。这类报告里带“↑”的整行会作为异常标记保存，搜索时以上下文摘录显示；没有标记的行不在任何已确认字段里，搜不到。这一缺口没有在本次处理。

识别层的误读原样保留在转录里，需要用户在复核时修正：“↑”读成“个”或“T”，“白”读成“自”，“U/L”读成“UIL”，“<”读成全角“＜”。图片报告的异常标记只取到“6.85↑”这样的数值格，不带项目名，这是既有行为。

12 份报告的库里，每个搜索词在 debug 测试进程中的首页用时为 2–13 ms。

## 叙述命中按句呈现的复测（2026-10-15）

[2026-10-15 决策](decisions.md)让没有命中表格行的报告按句列出检查结果与结论里的命中。为此在搜索词落在卡片没有显示的字段时，要确定这两个字段的位置（第一次读取详情，之后按摘要记住），并对两个较长的字段做按句查找。

### 方法

- 环境同上。资料库用未经改动的 `logical-generate --reports 9990` 生成：9,791 条已确认记录和 199 份草稿，用时 340 s，数据库 375,312,384 bytes。这次没有改生成方式：检查结果是约 600 字的合成词串、结论约 120 字，都没有句号等句末标点，所以每个字段整体算一句，命中句按摘录的规则截取。这是叙述字段最长、最不利的形状。
- 查询：`logical-queries` 的六个固定词，另加一个临时词 `偏高`，它只出现在检查结果、结论和异常标记里，不在标题、机构或日期里。`合成` 出现在每份报告的每个字段里。
- 对照：同一个二进制、同一个资料库，用临时环境变量切换三种模式（环境变量、临时查询词和“首次”计时都是临时改动，结束后已撤回）：不做呈现（基线）、只做摘录（与前一版行为相同）、按句呈现（本次）。每个词 20 次采样取首页，取法同上；“首次”是该进程里第一次取这个词的首页。
- 初版按句呈现在 `合成` 上比只做摘录慢约 8 ms：判断字段是否已在卡片显示之前，先对每个候选字段做了一次完整查找；按句截取时又把整句复制一遍、重新查找一次。改为只用前缀比较判断“已显示”、在原文里直接截取已找到的命中、按 Unicode 标量找句末之后，复测如下。

### 结果

首页时间，单位 ms，格式为 p50 / p95（首次）。基线不经过呈现代码，取优化前的第一轮；另两列取优化后的第一轮。每种模式都跑了两轮，同一模式两轮的 p50 相差不到 2 ms。

| 查询 | 命中数 | 基线 | 只做摘录 | 按句呈现 |
| --- | ---: | ---: | ---: | ---: |
| 无匹配 | 0 | 27.7 / 29.6（29.3） | 29.0 / 30.3（30.4） | 28.6 / 29.4（30.3） |
| 稀有词 | 1 | 28.5 / 31.5（28.3） | 30.5 / 31.4（29.5） | 28.9 / 30.1（29.3） |
| 日期 | 93 | 36.2 / 38.9（35.2） | 36.9 / 38.0（36.2） | 36.8 / 37.7（37.2） |
| 中文短词 `合成` | 9,791 | 34.5 / 35.5（34.8） | 38.6 / 40.8（39.1） | 43.3 / 44.8（48.3） |
| 成员 | 9,791 | 34.8 / 36.1（34.6） | 36.0 / 37.2（36.6） | 36.5 / 38.5（37.2） |
| `偏高` | 9,789 | 59.7 / 67.3（60.2） | 66.0 / 67.7（65.4） | 66.9 / 68.6（66.7） |

进程峰值 footprint 在 80–84 MB 之间，三种模式没有可分辨的差别。

### 边界

- 与只做摘录相比，`合成` 的首页 p50 多约 4.5 ms，首次多约 9 ms（首次要为前 100 份报告各解码一次详情以确定字段位置）；`偏高` 多不到 1 ms；其余查询相差在 2 ms 以内。`合成` 与基线相比多约 9 ms，p50 43.3 ms，低于 50 ms 门槛。
- `偏高` 的基线本身是 60 ms，已高于 50 ms 门槛：预筛键对这些合成词串排除不了多少字段，Foundation 要在九千多份报告的 600 字字段上确认。这与本次功能无关，2026-10-12 的复测用的是同样的数据形状，但没有测只出现在叙述字段里的词。
- 真实超声报告一般带句号，每句更短，按句查找的开销预计更小，但没有测。只测了 Platform repository 到 DTO 的时间，界面渲染、macOS 26 和 OS 冷缓存都没有测。
